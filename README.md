# Provider-integrator-Ruby

Генератор Ruby-интеграций платёжных провайдеров по OpenAPI-спецификации: разбор эндпоинтов, маппинг статусов, ошибок и полей, генерация сервиса, документации, фикстур и самотеста. Детерминированные правила, без нейросетей.

**Состояние:** 91 тест проходят, включая восемь сквозных: генерация по спецификации → проверка синтаксиса результата → реальный прогон сгенерированного самотеста. На эталонной спецификации NovaPay — 28 из 28 элементов распознаны автоматически. Одна и та же логика без правок кода отрабатывает на десяти разных спецификациях, включая композицию `allOf`/`oneOf`, ключ в query-строке и рекурсивные схемы.

## Что делает

Подключение нового платёжного провайдера в Space Payments — это Ruby-сервис с единым контрактом `Provider::BaseService` из четырёх методов. Руками это занимает 2–5 дней на провайдера. Инструмент принимает открытую спецификацию API и выдаёт готовый комплект интеграции.

- Разбирает OpenAPI 3.x собственным загрузчиком: резолвит вложенные `$ref`, читает параметры (с перекрытием параметров пути параметрами операции), тела запросов, ответы, схемы авторизации и примеры
- Определяет роль каждого эндпоинта — создание, статус, отмена, webhook — по эвристикам метода, пути и формы запроса
- Находит вебхук четырьмя способами: по имени пути или операции, разделом `webhooks:` из OpenAPI 3.1, разделом `callbacks:` внутри операции из OpenAPI 3.0 и по косвенному признаку — публичный POST с телом там, где остальные эндпоинты требуют авторизации. Последний случай помечается в отчёте как требующий проверки, а в спецификации без объявленной авторизации не применяется вовсе: там публичны все эндпоинты и признак ничего не значит
- Сопоставляет статусы, HTTP-коды ошибок и поля запроса с каноническими значениями Space Payments по редактируемым словарям
- Определяет алгоритм и кодировку подписи вебхука из описания заголовка
- Генерирует сервис, руководство по интеграции, фикстуры и самотест, который реально прогоняет сгенерированный код по HTTP
- **Не додумывает то, чего нет в спецификации:** нераспознанное попадает в отчёт, в `TODO` внутри кода и в раздел документации «Требует ручного решения»

## Быстрый старт

Требуется Ruby 3.2+ (проверено на 4.0.6). Единственная внешняя зависимость — `rspec`, и та нужна только для тестов.

```bash
git clone https://github.com/SeMe4K-0/Provider-integrator-Ruby.git
cd Provider-integrator-Ruby
bundle install
./integrate --spec specs_examples/provider_api.yaml --provider novapay --lang ruby
```

Результат появится в `./output/novapay/` — каталог по умолчанию свой для каждого провайдера, чтобы файлы разных интеграций не смешивались.

## Использование

```bash
./integrate --spec PATH [--provider NAME] [--lang ruby] [--output DIR] [--dry-run]
```

| Флаг | Назначение |
|------|------------|
| `--spec` | путь к спецификации OpenAPI 3.x (обязательный) |
| `--provider` | имя провайдера: определяет имя класса, файлов и переменной окружения |
| `--lang` | целевой язык, сейчас поддерживается `ruby` |
| `--output` | каталог результата, по умолчанию `./output/<provider>` |
| `--dry-run` | только разбор и отчёт, без создания файлов |
| `--debug` | печатать трейс при непредвиденной ошибке |

## Что генерируется

| Файл | Содержимое |
|------|------------|
| `<provider>_service.rb` | сервис по контракту `Provider::BaseService`: `check_conditions`, `create_request`, `fetch_status`, `process_callback`, плюс `cancel_request`, если отмена есть в спецификации |
| `INTEGRATION.md` | авторизация, таблица методов, маппинг статусов и ошибок, тело запроса, конфиг ProviderGateway, схема подписи, список нераспознанного |
| `fixtures.json` | примеры запросов, ответов и уведомлений из спецификации плюс граничные случаи |
| `<provider>_integration_self_test_spec.rb` | самотест: поднимает мок провайдера и прогоняет полный цикл |
| `provider_base_service.rb`, `mock_provider_server.rb` | заглушки контракта и мок, чтобы комплект запускался отдельно от репозитория |

Фрагмент сгенерированного сервиса:

```ruby
STATUS_MAP = {
  "pending" => "in_progress",
  "completed" => "approved",
  "failed" => "rejected",
}.freeze

def build_payload(operation)
  {
    amount: (operation.amount * 100).to_i,
    currency: "RUB",
    external_id: operation.id,
    recipient: {
      type: "sbp",
      phone: operation.payout_requisite.dig("sbp", "phone")
    }.compact
  }.compact
end
```

## Как добавить провайдера

В обычном случае — никак: достаточно передать его спецификацию. Правила меняются в `config/rules/`, код при этом не трогается.

| Файл | Что настраивает |
|------|-----------------|
| `statuses.yml` | имена поля статуса и синонимы значений → `in_progress` / `approved` / `rejected` |
| `errors.yml` | HTTP-код → внутренний код ошибки и действие (`reject`, `retry`, `retry_backoff`, `fetch_status`, `alert_and_block`, `alert_and_retry`) |
| `field_aliases.yml` | имена полей запроса, разделённые на обязательные и относящиеся к способу выплаты |
| `signature_schemes.yml` | ключевые слова описания заголовка → алгоритм и кодировка подписи |
| `operation_sources.yml` | выражения Space Payments, из которых берутся значения полей |
| `heuristics.yml` | признаки ролей эндпоинтов, заголовка подписи, минорных единиц суммы и способа выплаты |

Например, статус `manual_review` у демо-провайдера CardPay намеренно оставлен нераспознанным — генератор о нём сообщает, а не угадывает. Одна строка в `statuses.yml` закрывает вопрос:

```yaml
canonical:
  in_progress:
    - manual_review
```

## Тестирование

```bash
bundle exec rspec
```

| Файл | Что проверяет |
|------|---------------|
| `spec_loader_spec.rb` | разбор NovaPay, резолв `$ref`, четыре вида некорректного входа |
| `ir_spec.rb` | структуры промежуточной модели |
| `semantic_analyzer_spec.rb` | роли эндпоинтов, оба способа описания вебхука, его отсутствие |
| `data_mapper_spec.rb` | таблицы статусов и ошибок, вложенные поля, подпись, незнакомый статус |
| `pipeline_spec.rb` | состав файлов, синтаксис результата, содержимое сервиса и документации |
| `universality_spec.rb` | три спецификации подряд: Bearer, поле `state`, синонимы полей, отсутствие вебхука |

Отдельно проверяется, что сгенерированный код работает, а не просто похож на код:

```bash
ruby bin/integrate --spec specs_examples/provider_api.yaml --provider novapay
bundle exec rspec output/novapay_integration_self_test_spec.rb
```

Самотест поднимает локальный мок провайдера, прогоняет создание операции, запрос статуса и обработку уведомления с реально вычисленной HMAC-подписью, а также проверяет отказ при неверной и отсутствующей подписи.

## Ограничения

Заявлено ровно то, что реализовано:

- **`allOf` сливается, из `oneOf`/`anyOf` берётся первый вариант.** Провайдер, у которого способы выплаты различаются вариантами схемы, потребует отдельной ветки интеграции для каждого — генератор об этом сообщает, но вторую ветку не пишет
- **Тело запроса собирается как JSON.** Схема читается из `application/json`, любого `*+json` или `x-www-form-urlencoded` (с предупреждением), но отправляется всегда JSON. XML и multipart не поддерживаются
- **Рекурсивная схема разбирается не до конца:** ветка обрывается на повторной ссылке, вложенные уровни в модель не попадают. Разбор при этом не прекращается, а факт обрыва попадает в отчёт
- При нескольких кандидатах на одну роль (два эндпоинта создания, два статуса) берётся первый по порядку в спецификации — с предупреждением в отчёте
- Схемы `oauth2`, `openIdConnect` и `http digest` распознаются, но заголовки авторизации для них не генерируются: в коде остаётся `TODO`
- Поддерживается OpenAPI 3.x; Swagger 2.0 отклоняется с понятным сообщением
- Ссылки `$ref` — только внутренние, на этот же файл
- Тело запроса разбирается на глубину одного уровня вложенности — этого достаточно для платёжных API и защищает от неограниченной рекурсии
- Алгоритм подписи вебхука OpenAPI формально не описывает, поэтому он определяется по тексту описания заголовка; когда ключевых слов нет, берётся дефолт и предположение помечается как неподтверждённое
- Целевой язык генерации — Ruby

## Источники и технологии

- Ruby 3.2+ (проверено на 4.0.6), стандартная библиотека: `yaml`, `erb`, `json`, `openssl`, `net/http`, `socket`, `optparse`
- [RSpec](https://github.com/rspec/rspec) (MIT) — единственная внешняя зависимость, используется только в тестах
- Спецификация [OpenAPI 3.x](https://spec.openapis.org/) — формат входных данных
- `specs_examples/provider_api.yaml` — спецификация из условия кейса Space Payments; `cardpay_api.yaml` и `bankex_api.yaml` написаны для демонстрации универсальности

Нейросети в решении не используются: разбор спецификации и все сопоставления выполняются детерминированным кодом и редактируемыми словарями правил.
